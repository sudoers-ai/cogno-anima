# EGO — executor and tool dispatch

Moved verbatim from `CLAUDE.md` on 2026-11-08: the contract did not change. `CLAUDE.md` keeps a short summary and points here. Update this file in the same pull request as any change to the EGO stage, as `CLAUDE.md` used to be updated.

4. **EGO** (`cogno_anima/stages/ego.py`, class `EgoStage`) — executor & tool dispatch:
   - Requires `ctx.noumeno` + `ctx.intent`. Signature is `process(ctx, backend, dispatcher, *, system_prompt)` — `backend: LLMBackend`, `dispatcher: ToolDispatcher` (host-injected), `system_prompt` is the persona's **execution** prompt (host).
   - **EGO = executor, SUPEREGO = locutor.** The EGO runs an agent loop (decide tool → `dispatcher.execute` → feed result back → repeat) and gathers data; it does **NOT** write the user reply. `EgoResult` is a trace (`steps` = source of truth; `tools_executed`/`draft`/`has_side_effects` derived) + a `draft` (the model's last text) for the SUPEREGO to voice. There is no `response`/`response_source` and no `returns_raw_json` (presentation left the EGO).
   - **NER signal enrichment in `_task_context`** (prompt hints): user `intent.constraints` / `intent.negation` are surfaced as `Constraints (must respect)` / `Must NOT` so the loop honors explicit restrictions. Two course-correction hints ride the same block: a deteriorating `intent.sentiment` (the contact is losing patience) and `ctx.metadata["circling_streak"]` — a HOST-counted number of consecutive turns its anti-repeat guard had to act on, which from `EgoStage.CIRCLING_MIN` (2, overridable; 0 disables) tells the executor it keeps arriving at the same answer. The host must recompute the streak every turn (a stale one warns forever), and an unusable value degrades to 0 rather than raising — a prompt hint must never abort a turn.
   - **Three confirmation gates (capability, not prompt-hints — `docs/ACT_CONFIRM_READONLY.md`).** Tool classification is host-declared via the optional `ToolPolicyDispatcher` Protocol (`is_mutating`/`requires_confirmation`, probed with `isinstance` like `ToolCallingBackend`); the core never hardcodes which tools mutate. **(A) Read-only mask** — when the host sets `ctx.metadata["ego_readonly"]` (acting on the ID's `needs_confirmation` signal because the *user* was tentative), the EGO offers ONLY non-mutating tools and `force_first` is off → it consults + proposes, never commits. **Fail-safe:** no policy → mask ALL tools (propose via draft). **(B) Confirmation gate** — a `requires_confirmation` (destructive) tool the model picks is **never executed** without `ctx.metadata["ego_confirmed"]`; the core holds it, records `EgoResult.pending_confirmation`, and stops to propose (the host runs its confirm UX → next turn with `ego_confirmed` → executes). **Opt-in** (no policy → no gate). **(C) The SKILL asks** — a `ToolResult(needs_confirmation=True)` says the skill RAN, decided it must not commit, and is asking about THIS call: the EGO records it as pending and stops, exactly like B, and the proposal text is the skill's own `output`, grounded in what it just read. It exists because B is per tool NAME and decided BEFORE execution, so it cannot know that cancelling *this* appointment is two hours away, or that *this* entry is a hundred times the usual one — the skill knows, because it read. A `True` is a **promise that nothing was committed**: the call is recorded `ok=False`, so `committed_this_turn` (which needs `ok` AND `side_effect`) can never count a proposal as a write, however the skill fills the other fields. The judge renders such a held call `→ PROPOSED (held for the user's confirmation; nothing executed)` with its output (`types.is_skill_proposal`; a call held by NAME carries `HELD_BY_NAME_PREFIX` and renders as before), never `ERROR`, and the held-message rule counts that output as a READ for that same call's held message and nothing else (0.1.2). The confirmation reaches the skill through the channel the host already owns (the skill's own context/metadata — `cogno_cortex.ToolContext`); **the core never invents an argument name**, because what a skill needs in order to commit is the skill's business. A confirmed call whose skill STILL asks committed nothing and there is nobody left to ask, so `_refuse_if_still_asking` fails it LOUDLY (`ok=False`, named error) rather than shipping "done" over a turn that wrote nothing — applied on BOTH routes a confirmed call arrives by (the deterministic replay and the model re-issuing inside the loop), because the first cut guarded only the replay and the loop counted the proposal as a commit. **A retenção de B e C é por CHAMADA, não por turno** — ela para o LAÇO, não o PASSO: um passo com duas chamadas segura a que pediu e executa a irmã, então o turno pode dizer "estou a segurar" e "comitei" ao mesmo tempo. Comportamento herdado (medido idêntico no gate B), mas a fonte C alarga o ALCANCE: o B só dispara em tool que o host declarou destrutiva, o C pode ser levantado por qualquer skill em qualquer chamada. A is broad (user unsure → mask all writes), B is surgical (dangerous tool → hold that call), C is specific (this call, on this data → propose); all three are propose/commit, all three keep "core signals, host decides". **C supersedes the ID's `needs_confirmation` in practice:** that one guesses from how the user PHRASED the request and has no reader; this one is a fact about what the skill found. **How long a hold LIVES is the host's, and the two-turn drawing is a shape, not a promise that the answer comes next** — a hold is `EgoResult.pending_confirmation` for exactly one turn, and only a host stamping `ego_confirmed` makes it survive. Measured in `cogno-host` 2026-09-05: a proposal, one unrelated question, then "sim" — the session state was rebuilt each turn, nothing was held by the third message, and the model answered "Vou agendar…" with zero tool calls. The property a host may not break, now written where the gates are (`docs/ACT_CONFIRM_READONLY.md`): **nothing is executed that was not re-proposed to the contact** — carrying a hold across turns without that rule trades "the proposal is forgotten" for "an ambiguous yes commits", which is the worse of the two.
   - **Dual-path FC:** a backend satisfying `ToolCallingBackend` (separate optional `Protocol` in `llm/base.py`, NOT folded into `LLMBackend`) uses native function calling; a plain `LLMBackend` (a stub, the distilled student, the default `OllamaBackend`) uses the **text-fallback path** — the model emits `<TOOL_CALL>` tags read by `parse_tool_calls_from_text` (`llm/tool_parsing.py`, ported from the parent; also rescues FC leaks). On fallback the tool list + `<TOOL_CALL>` mechanics are rendered into the prompt; on native they travel via the API.
   - **Execution is delegated** ("EGO = brain, dispatcher = hands"): the core never touches the DB/MCP/API, so atomicity/rollback/outbox are **host** concerns. `ToolResult` (`output, ok, error, side_effect`) carries no `compensating_tool` (compensation is host-internal). Error contract: recoverable failure (`ToolResult(ok=False)`) is fed back so the model self-corrects; fatal (`MCPDispatchError` raised by the dispatcher) propagates; a stray exception is wrapped in `ToolExecutionError` and propagated (the EGO never guesses recoverability).
   - **Loop policy:** `max_steps = ctx.metadata.get("ego_max_steps", default)` where `default` is 5, or 8 when `intent.is_composite` (a multi-task request gets more budget; the host's explicit `ego_max_steps` always wins); `intent.is_sequential` adds an **ordering instruction** + the `causal_chain` as a numbered supporting plan in the task context (the loop still decides real tool order). Stop when the model emits no tool_calls (→ `draft`); `tool_choice="required"` on the 1st iteration for `ACTION_REQUEST`; hallucinated tool name → recoverable feed-back; **duplicate-call detection** (ported from parent: same `(tool,args)` blocked after 2 repeats, abort after 2 all-blocked steps). Budget/convergence bounds are **signals** (`interrupted=True` + partial result), not exceptions. Correction loop (EGO↔SUPEREGO, run by the orchestrator — `cogno-soma`'s `Pipeline.run_turn`, or a host's own glue): `ctx.metadata["ego_correction"]={reason,attempt}` drives an `[ACTIONS ALREADY EXECUTED]` block built from the prior `ctx.ego_result`; the core renders whatever trace the host hands back (host rollback → empty trace → fresh retry).
   - **The prompt leaves a record, and never its text (0.1.5, 2026-10-07).** The executor was the one stage whose prompt left nothing behind — the voice, the judge and the scope guard each have an inventory — and it is the stage that ACTS. Measured downstream: it proposed the text of the LAST DELIVERY instead of the proposal that was waiting, and nothing persisted could say which part of its prompt had shown it that text. Four fields on `EgoResult`, filled on every `process` call:
     - `prompt_blocks` — `[{"block": slug, "chars": n}]`, the fourth inventory of the family. The slugs come from the closed `ego.EGO_BLOCKS` (exported as `EGO_PROMPT_BLOCKS`): `persona`, `task_context`, `context`, `context_data`, `actions_done`, `correction`, `available_tools`, `tool_calls`.
     - `prompt_text` — the rendered system prompt, IN MEMORY, never persisted or logged by the core (the rule of `SuperegoResult.prompt_text`). Cut a part out with `EgoStage.prompt_block(prompt_text, prompt_blocks, slug)`, which refuses when the lengths do not add up.
     - `prompt_sha` — the digest of what the attempt STARTS from (system prompt, task, and on the native path the tool schemas; never a tool result), through `prompts.prompt_digest`. A per-ATTEMPT label, because the contact's words are inside it; `metrics.prompt_sha` stays the deployment-level one. `None` = not on record.
     - `prompt_path` — `native` | `fallback` (`VALID_EGO_PROMPT_PATHS`). It tells "no `available_tools` row because the API carried the schemas" from "because the catalogue was empty".

     **It is taken from the PARTS, not scanned from the text, and that is measured.** Three of the eight parts have no header of this library's (the host's persona prompt, `mk.EGO_CONTEXT`, the fenced `mk.EGO_CONTEXT_UNTRUSTED`), so a scan over the five headers gave the persona no row and filed the whole context under `task_context` — 2081 characters against a real 88, on a prompt of 2556. `_system_parts` returns `(slug, text)` and has two readers, `_build_system` (the join) and `prompt_inventory` (the lengths), so the record cannot describe another prompt. The pair: `sum(chars) + 2 * (rows - 1) == len(prompt_text)`. Giving the context a header would have made a scan work and changed the bytes of every turn's prompt; it was refused.

     **The prompt did not move by a byte.** `tests/unit/test_ego_prompt_inventory.py` holds 47 digests taken on `1923c85` (native or text × notes × data × correction × prior actions, plus the edges), with a control. Three cells joined in 0.1.6 with the guard on the retry block: a fence tag in an argument of a committed call, its clean control, and a header forged inside the correction's reason (the two prompts that change moved). It is a landing-time proof: regenerate it when the executor's prompt changes on purpose. The same file pins `EGO_BLOCKS` to the rendered prompt both ways, and `reserved_headers()` — which now reads that table — to the 36 headers it had, plus the one the judge's table gained in 0.1.6 (the consult section).

     **Per attempt.** The prompt is assembled once per `process` and re-sent on every step; a correction retry builds another. `ctx.ego_result` is REPLACED on each retry, so a layer that wants every attempt's record copies it before the next one runs (cogno-soma's ledger). A forged header adds no row here: a row is a part the builder made.
   - Tokens summed across the loop into one `StageMetrics(model=backend.model)` (embeddings 0); folded into `PipelineContext` totals via `ctx.ego_result` + `ego_metrics` (like `id_metrics`). **Out of scope (host):** persona/MCP/skill-selection/RBAC, KG/history retrieval, mobile brevity + voicing (SUPEREGO), model-ladder, atomicity. A standalone embedding `ToolRetriever` for large catalogs is left to the host (the EGO trusts `dispatcher.tools_schema()` as final). When a persona draws tools from several sources at once (in-process skills via `cogno-cortex`, an MCP client, host-native functions), the host merges them with `cogno_anima.tools.CompositeDispatcher` — a `ToolDispatcher` (+`ToolPolicyDispatcher`) whose `tools_schema()` is the union (first source wins on a name collision) and whose `execute()`/policy methods route to the owning source (a non-policy source is treated conservatively: assumed mutating, no confirmation gate). The EGO still sees one flat tool set; the *contract* is the unifier — skill/MCP/native are just sources behind it. **The router also forwards `source_requires_confirmation`** — *did the SOURCE itself declare this destructive*, as opposed to *it is a write and nobody exempted it*, which `requires_confirmation` flattens together. A host layering a blanket "every unexempted write confirms" rule over each source exposes the finer predicate on its wrapper, and a caller above the router (an anti-holding floor, say) needs the two apart. The fallbacks follow the SAME conservative convention as the two methods beside it: the finer predicate when the source has it; otherwise a policy source's own `requires_confirmation` **is** the source verdict (answering `False` there would waive a tool the source really did mark destructive); a non-policy source declared nothing. **This was measured, not designed:** the router defined neither the method nor `__getattr__`, so a host floor reaching for it through the wrappers hit this class and fell back to holding — and a contact who asked for a human was answered "shall I proceed?" instead of being transferred. A generic `__getattr__` forwards everything a WRAPPER does not mediate (one layer, one source) and is the wrong answer for a ROUTER over many: it cannot know which source to forward to. It is **also** the wrong answer for the two POLICY methods even on a wrapper — Python 3.12 resolves `runtime_checkable` protocol members with `inspect.getattr_static`, which never calls `__getattr__`, so the wrapper vanishes from the probe and the confirmation gate stops firing entirely. Those bind onto the INSTANCE, conditionally, via `cogno_anima.tools.bind_delegated` (below).
